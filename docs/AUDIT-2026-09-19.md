# Upllyft Platform Audit — 19 September 2026

Read-only analysis of the monorepo covering security, performance, and engineering gaps.
Method: five parallel code investigations (auth/authz, application security, backend
performance, frontend, engineering quality) plus live probes against the running app
(API on 3001, web-main on 3000), a Lighthouse pass, and `pnpm audit`.
Every finding below was spot-checked against the source before being included.
Paths are relative to the repo root. Severity: Critical / High / Medium / Low.

---

## 0. Corrections to assumptions in CLAUDE.md

- The API runs on **Express**, not Fastify. `apps/api/src/main.ts:15` calls `NestFactory.create` with no adapter, and uses `express-session`, `cookie-parser`, `express.json`. `fastify` is a devDependency only.
- `pnpm --filter @upllyft/api prisma:migrate` does not work on a fresh DB (see §6). `prisma/baseline/README.md` documents the real recovery path.
- `GET /api/health` returns 404. The health route is at root `/health` because the global prefix excludes it.
- Redis is provisioned in `.env` but **nothing in the API uses it**. All caches, sessions, throttling, and Socket.IO rooms are in-process memory.

## 4. Backend performance

**Measured on this machine:** process start to Nest listening took ~6 minutes. The log shows "Starting Nest application" was printed 5m45s after launch, so **module loading** (require phase) dominates, not DI or DB. Nest DI then took ~20 s, and "Database connected successfully" was printed **four times**. Once up, the API answers a trivial route in ~10 ms (the ~230 ms seen via `localhost` is a Windows IPv6-first artifact; use `127.0.0.1`).
